# data-qd-222 · 配置发布与回滚

配置发布者暂存一份不可变版本，随后用代数比较原子切换当前配置。服务实例通过轮询只接收更新；回滚指向旧内容时仍产生新代数，因此实例能识别这一变更。过时的发布请求会被拒绝。当前是单通道和整份配置替换，未提供实例确认或分批策略。

Python 3.9+，仅标准库。示例使用本仓合成配置和临时数据库。

```sh
python3 -B -m unittest -v                 # 全部验收（含 test_reclaim.py）
python3 -B -m unittest -v test_reclaim    # 仅暂存版本回收
python3 -B -m unittest -v test_recovery_copy  # 仅灾备演练（恢复副本与换库轮询）
python3 -B -m unittest -v test_hot_reload # 仅边缘节点热切（作业准备、节点验准、值班工单）
python3 -B demo.py
```

实例依次读到 `(1, 1, ...)`、`(2, 2, ...)`、`(3, 1, ...)`；过时切换会输出 `stale write rejected`。

## 带流量上限的代表性试发

全量切换前可以先走一轮试发：每个可用区恰好一台实例试用候选，同时覆盖清单里出现过的所有配置运行时，且所选实例负载之和不超过预算。择优先最小化总负载，再按区名升序的实例 ID 元组做字典序决胜；同库同时最多一个活动试发，试发期间普通 `poll` 仍只返回上一份全量配置。

```python
trial_id, selected = publisher.begin_canary(
    revision, expected_generation=generation,
    roster=[(instance_id, zone, runtime, load), ...], max_load=budget)
subscriber.poll_canary(trial_id, instance_id)   # None 或 (trial_id, revision, config)
subscriber.ack_canary(trial_id, instance_id)    # 必须先取到候选，重试幂等
publisher.finish_canary(trial_id)               # 集齐确认才原子切全量，返回新代数
publisher.abort_canary(trial_id)                # 只关闭试发，不动全量指针
```

试发名单在开启时快照进数据库（不保存原始清单），活动期间旧 `promote` 会抛 `ConflictingPromotion`；`finish_canary` 在同一事务里关闭试发并推进代数，跨连接竞争时最多一方成功、代数只前进一次。试发 ID 由 `AUTOINCREMENT` 分配，关闭后也不复用；新建指向同一数据库的对象即可继续参与活动试发。试发表仅通过 `CREATE TABLE IF NOT EXISTS` 追加，旧数据库可直接打开。

## 配置组：相互依赖组件的原子发布

一条网关可能同时依赖路由、上游、限流等组件，且某个路由版本会精确要求某一版上游。配置组路径让发布者一次提交相互依赖的整批变更，订阅者只安装自己根组件及其递归依赖闭包内的那部分。配置组有独立的组代数（空组为代数 0），与单通道的 `generation` 互不推进；组绑定只引用 `stage` 产生的同一批不可变 revision，不复制配置正文。所有新表均以 `CREATE TABLE IF NOT EXISTS` 追加，已有数据库无需重建即可使用。

```python
epoch = publisher.publish_group(
    {"route": (revision, {"shared": shared_revision}),   # 整体替换绑定
     "shared": (shared_revision, {}),
     "obsolete": None},                                   # 删除（不存在也算有效变更）
    expected_epoch=epoch)
reply = subscriber.poll_group(("route",))               # 首拉：mode="full"
reply = subscriber.poll_group(("route",), known_epoch=reply["epoch"])  # 无变化时为 None
```

发布对整批生效后的组做校验，而非逐条变更的中间状态：每条 `needs` 必须指向组内同名且版本完全相等的组件（精确版本，不是下限），组内不得有依赖环，未改动的组件也不能因本批失去依赖。一次成功恰好推进一个组代数并返回它，即使提交的绑定与之前完全相同；非法参数、悬空或错版本依赖、环及整组超过 2048 个组件抛 `ValueError`，直接绑定未暂存的 revision 抛 `KeyError`，组代数不符抛 `ConflictingPromotion`，且任何拒绝都不改动组内容、代数与历史。不同连接以同一旧代数竞争时只有一方成功。

`poll_group` 接受 1–16 个互不相同的根组件名（元组，顺序无关），暂未发布的根视为空，允许提前订阅；实例换根时调用方以 `known_epoch=None` 重新整体拉取。回复是同一组代数下的一致快照：

- `full`：首拉，或 `known_epoch` 已早于保留窗口；`put` 为当前完整订阅范围，`remove` 为空，订阅者整体替换这组根管理的本地配置。
- `delta`：按实例实际安装的旧依赖范围与当前范围做差，只下发新增或 revision 变化的组件，`remove`（升序元组）列出已不在范围内的组件。组件仍在组内但已离开本实例范围时也会卸下；只要任一根仍依赖它就不会卸下。即使变化发生在其他订阅范围，也返回空增量和新代数。
- 已报告当前代数时返回 `None`；负数、布尔值、未来代数及非法根参数抛 `ValueError`。轮询与发布重叠时，回复固定在发布前或发布后的单一数据库时点，不会拼接混代内容。

重开数据库后仍可精确追赶最近 256 个组代数（含当期）。窗口装满时，掉出窗口的最早代数被折叠进移动基线（`group_base`），其事件日志被删除——每代只存相对上一代的变更行，从不保存全组副本，因此长期切换的空间开销与代数无关。

## 暂存版本的安全回收

下线服务或结束试发后，废弃版本的正文不会自动消失；但也只有**显式登记**过的版本才可能被回收。登记不删正文，也不撤销任何既有或未来的合法引用：在真正回收前，该版本仍可用原接口发布。

```python
publisher.retire_revisions((revision_a, revision_b))  # 登记待回收，可重复提交
pin_id = publisher.pin_revisions((revision_a,))       # 值班保留单，返回正整数 ID
publisher.read_pin(pin_id)                            # {revision: config}，未知/已释放为 None
publisher.unpin_revisions(pin_id)                     # 首次释放 True，其后/未知 False
publisher.collect_retired(after=0, scan_limit=64)
# {"deleted": (...), "retained": (...), "next_after": ...}
```

- 批量接口的 `revisions` 是 1–32 个互不相同的版本 ID 元组，顺序无关；ID 须为 1 到 2⁶³−1。形状非法、重复、越界或布尔值抛 `ValueError`；批次中含格式合法但不存在的版本抛 `KeyError`，且整批不生效（不会部分登记或部分保留）。
- 保留单不复制正文、不能改成员，重开数据库后仍有效；同一批可以有多个保留单，`unpin` 只释放指定的那一张，只要还有另一张持有该正文就仍受保护。释放不会自动删除版本，也不会取消其待回收登记。
- `collect_retired` 按版本 ID 升序检查严格大于 `after` 的待回收版本，最多 `scan_limit`（1–64）个。受保护项占用检查名额但不删除。若本批之后还有更大的待回收 ID，`next_after` 为本批最后检查的 ID，否则为 `None`；从 `0` 重新开始下一轮即可。合法 `after` 为 0 到 2⁶³−1。
- 保护来源在同一个原子事务里判断并删除：当前全量指针、活动试发候选、任何未释放保留单，以及配置组 256 代保留窗口内任一代（含当期与窗口最老一代）仍绑定的版本。落在窗口外的旧绑定不再保护。并发下先取得引用者保留正文；回收先成功时，随后引用该版本会得到原有的“未知版本”错误。
- 回收不推进任何发布代数、不缩短组窗口、不关闭试发、不影响轮询。删除腾出的空间留在 SQLite 页中供后续复用，不要求数据库文件立即缩小；已删除版本不留永久墓碑。
- `stage` 的版本 ID 高水位单独持久化，即使回收删空库存、重开数据库后再暂存，也会发放比历史上任何已发放 ID 都大的 ID，旧发布请求或旧保留单不会误用新正文。

已有数据库原地升级：新表均以 `CREATE TABLE IF NOT EXISTS` 追加，旧数据及原有调用方式保持不变；升级前暂存、从未登记的版本不会被自动回收。

## 本地灾备演练：恢复副本与订阅者换库

主库仍在接收发布时，值班人员可以复制出一个可独立发布的恢复库，把一批配置组订阅者切过去演练，再切回主库。组代数只在单库内有意义：两个库各自发布一批后可能恰好处在相同代数，订阅者却安装着不同内容。因此每个库携带一个分支标识（branch）——32 个小写十六进制字符，旧库升级后首次打开时随机获得，重开不改变——订阅者改用 `(branch, epoch)` 游标轮询，换库时不会把旧安装误认为已同步。

```python
branch = publisher.fork_recovery("drill/recovery.db")   # 返回恢复库的分支标识
reply = subscriber.poll_group_cursor(("route",), cursor=None)          # 首拉或换根
reply = subscriber.poll_group_cursor(("route",), cursor=reply["cursor"])
```

`fork_recovery(destination)` 从当前文件库生成一个独立的新 SQLite 文件：

- 副本对应从调用开始到目标文件出现之间源库的**同一个已提交时点**：全量指针与代数、当前配置组和原有 256 代可追赶窗口、暂存正文与版本发号高水位、回收登记及值班保留单都来自该时点。复制走 SQLite 在线备份（逐页流式拷贝，只持读事务）：源库为 WAL 模式时，拷贝期间其他连接的发布与回收照常提交，不靠暂停写入或强制先完成 checkpoint 取得一致性；默认日志模式的旧库同样可以复制（该模式下写入不与复制并行）。
- 在途试发不带入副本：源库的试发照常继续，副本不能接着交付或确认它；副本可立即发起自己的试发，试发 ID 严格大于刚丢弃的 ID（`sqlite_sequence` 随复制保留）。清掉试发不推进任何发布代数，也不自动回收任何正文。
- 目标路径按"不存在才出现"发布：先在目标目录内写临时文件，完成后原子硬链接到最终路径。中途任何时刻最终路径要么不存在、要么是可直接 `Distribution(destination)` 打开的完整副本；目标已有目录项（含源库本身）抛 `FileExistsError`，同名竞争只许一个成功；父目录不存在按文件错误处理；复制或初始化抛错时不在最终路径留下半成品，也不破坏已有文件。副本脱离 WAL 辅助文件，单独移到另一目录也能打开。演练只接管新路径，不在原地替换运行中的库；断电后未发布的临时文件不要求清理。
- 每次成功复制都得到彼此不同、与源库不同的分支标识；源库标识不变。

`poll_group_cursor(roots, *, cursor=None)` 的根参数、回复形状与 `poll_group` 相同，非空回复额外携带 `cursor`，值指向回复实际使用的分支及代数；分支、代数与配置来自同一份读取快照。游标规则：

- `cursor=None` 表示首拉，调用方换根时同样用 `None`。
- 外库游标（分支不同）：无论代数相等、落在本库保留窗口内还是比本库更新，都返回当前分支的 `full`——这是受管安装的整体替换而不是叠加，`remove` 为空，只存在于另一边的组件靠整体替换卸掉；外库代数绝不做未来代数判定。
- 同分支游标走原有代数判定：当期返回 `None`，保留窗口内精确增量，过老回退完整替换，未来代数抛 `ValueError`。
- 游标非法（分支不是 32 位小写十六进制、代数为布尔值或超出 0 到 2⁶³−1、形状不对）或根参数非法抛 `ValueError`。旧接口 `poll_group` 的形状与语义不变，仍用裸代数的旧订阅者不受影响；跨库重放写请求或试发令牌不在本协议范围内。

演练规模保证：单库最多 2048 个现存暂存版本、每份配置的序列化正文最多 256 KiB、至多 64 张保留单（每张仍限原来的 32 个版本），组及试发继承现有上限——这些不是给旧接口加的录入限制。复制按页流式进行，恢复进程的峰值内存与库大小无关（验收用例：1024 份约 160 KiB 正文，单独恢复进程从启动至复制完成的峰值 RSS 不超过 96 MiB）。

## 边缘节点热切：作业准备、节点验准与值班工单

发布库可以原子提交整组配置，但老节点不能整组重载：它先把配置装入新的槽，再一次只切换一个入口（根）的整条依赖路由；只要还有入口在用，旧槽就不能腾出来。热切能力完全在调用方内存中完成，不新增服务、表或外部依赖，也不改动组历史。

槽由 `(组件名, revision)` 标识：同一槽被多个入口引用只占一份容量；不同组件即使复用同一个暂存 revision 也是不同槽；同一组件的不同版本可以同时装入。每个根切换的是它所属代的整条传递依赖路由（含根本身），而不仅是根自己的正文；根版本号不变、依赖范围变化时切换仍然有效且必须执行。

```python
job = publisher.prepare_hot_reload(
    ("A", "B", "C"), from_epoch=old_epoch, to_epoch=new_epoch,
    weights={("A", rev_a): 1, ("p", rev_p): 3, ...})  # 恰好覆盖作业全部槽
state = job.initial_state()          # 所有根仍按旧代服务，已装槽为旧侧并集
result = job.step(state, ("load", slot), capacity=cap)   # 获准才交付该槽精确正文
result = job.step(state, ("switch", "A"), capacity=cap)  # 一次切一个根的整条路由
result = job.step(state, ("unload", slot), capacity=cap) # 仍有根在用就拒绝
plan = job.plan(state, capacity=cap)
# {"required_capacity": 最小峰值权重, "actions": 可逐步交给 step 的工单或 None}
```

- `prepare_hot_reload(roots, *, from_epoch, to_epoch, weights)` 在**同一个 SQLite 读快照**里重建两个保留代的整组、取每个根在各自代的完整传递依赖范围（含根），读出两端绑定与正文。两个代数必须仍在 256 代保留窗口内且 `0 <= from_epoch < to_epoch`，布尔值不接受；根格式沿用 `poll_group`，每个根在两端都必须存在。目标代不必是当前代——绝不拿当前组替代指定端点，也不拿 `put/remove` 当完整依赖范围。作业对象一旦返回，后续发布改变不了它的端点、正文或步骤判定；作业只在内存中持有，不做跨进程续跑、持久化工单或组历史更改。
- 作业两端范围合计至多 128 个不同槽；每份正文按库存中的 JSON 文本计 UTF-8 字节，不超过 256 KiB。`weights` 是以这些槽为键的字典，必须**恰好**覆盖这些槽，每个权重是 1–1000000 的整数（布尔值拒绝）；容量算的是权重之和，不是槽数或正文长度。非法输入、端点掉出窗口或超出上限抛 `ValueError`，这些上限不约束旧接口。
- `initial_state()` 返回 `{"switched": (), "loaded": (...)}`，两个元组都无重复且按字面升序；`loaded` 恰好是旧端各根所需槽的并集。状态由调用方按本次作业的现场传入，允许预先多装作业内槽或先完成部分切换，但每个未切/已切根当下所需的旧/新槽必须都已装入，否则状态非法。
- `step(state, action, *, capacity)` 只验准并模拟单个真实操作，不实际动节点：
  - `("load", slot)`：槽必须属于本作业且尚未装入；装入后总权重不超过容量才获准，获准才在 `config` 里交付该槽的精确配置正文（每次重新解析，改写返回值不影响后续调用）。
  - `("switch", root)`：根必须属于本作业且尚未切换；其目标侧整条依赖必须已装齐。切换本身不装卸槽、不动别的根，不能把尚在服务的旧槽当作已腾出的预留空间。
  - `("unload", slot)`：槽已装入、且当前没有任何根在其当前一侧使用它才获准。
  - 形状合法但当前不能执行的动作返回 `None`，不交付配置、不改状态；状态、动作形状或标识非法（含不属于本作业的槽或根）、状态缺活跃槽、或现场已装权重超过本次容量，抛 `ValueError`。容量取 0–128000000 的整数，布尔值拒绝。三个接口都不修改调用方输入。
- `plan(state, *, capacity)` 从真实现场出发，用子集动态规划（状态是已切根集合，至多 2¹⁶；不遍历根的全排列）求达到终态的**最小峰值权重**，起始状态与"装齐新侧尚未切换"的瞬间都计入；卸载只会缩小驻留集、不抬高峰值。终态是所有根切到目标侧且只装着目标端所需槽的并集。即使实际容量不足（含小于起始权重的咨询场景）也回传确切门槛，此时 `actions` 为 `None`；容量够则返回能逐条交给 `step` 重放的工单，已达终态返回空元组。现场先做了别的获准动作或预算变化时，节点按本次传入的数据重新判定，值班也能从部分切换后的现场重新规划。工单不是执行凭据。
